# VCKG Control Dashboard

A professional React control plane (REST + WebSocket) layered **on top of** the
existing `student-system-creator` CLI. Nothing about the existing build /
validate / evaluate / package / serve behaviour changes — the dashboard launches
those exact commands as durable, streamed subprocesses and reads existing
challenge artifacts read-only.

## Architecture

```
React SPA (frontend/)  ──HTTP──▶  /api/dashboard/*   (FastAPI, dashboard/app.py)
        │              ──WS────▶  /ws/dashboard/*
        ▼
   JobManager  ──spawn──▶  python -m student_system_creator <build|validate|evaluate|package|serve>
        │
        ├─ log_parser  → structured DashboardEvents
        └─ outputs/dashboard/jobs/<id>/{job.json,events.jsonl,stdout.log,result.json}
```

- **Durable jobs**: every job persists to `outputs/dashboard/jobs/<id>/`. A
  browser refresh (or server restart) re-loads job state and replays events.
- **Resumable**: build/KG jobs resume from the existing KG cache; "Resume"
  simply relaunches the same spec.
- **Admin vs student mode**: a single masking switch in `inventory.py` decides
  what leaves the server. Student preview never exposes labels, original kg ids,
  the alias map, or the private registry.

## Install

Python backend dependency (FastAPI + uvicorn):

```powershell
pip install -e ".[dashboard]"
```

Frontend (one-time build):

```powershell
cd frontend
npm install
npm run build
```

## Start the production dashboard

```powershell
student-system-creator dashboard `
  --config student_system_creator/configs/default.yaml `
  --host 127.0.0.1 `
  --port 8080
```

Open <http://127.0.0.1:8080>. If `frontend/dist` is missing the backend serves a
helpful page telling you to build it; the API stays fully functional.

## Dev mode (hot-reload frontend)

Terminal 1 — backend with auto-reload:

```powershell
student-system-creator dashboard-dev --config student_system_creator/configs/default.yaml --port 8080
```

Terminal 2 — Vite dev server (proxies `/api` and `/ws` to the backend):

```powershell
cd frontend
npm run dev
```

Open the Vite URL (default <http://127.0.0.1:5173>).

## Pages

| Page | Purpose |
|------|---------|
| Overview | counts, label balance, disk, validation status, leakage check, quick actions |
| Live Dashboard | real-time progress + logs over WebSocket; cancel / resume |
| Projects | registry projects, smallest→biggest, select & build |
| Functions | candidate functions, select & build / audit |
| Build / Resume | wizard to launch `build` with mode/limit/backend/overwrite/force-rebuild |
| KG Explorer | in-browser bounded graph view (replaces static `index.html`) |
| Agent Audit | q1/q2/q3 agent query flow reconstructed from evaluation events |
| Validation | latest report + run validation |
| Evaluation | run a `solution.py`, view metrics (acc/precision/recall/F1, confusion) |
| Packaging | package RAID bundle with disk warnings |
| Settings | editable default paths/ports, persisted to settings JSON |

## What is NOT changed

- `student-system-creator build / serve / validate-challenge / evaluate / package-raid`
  behave exactly as before.
- Static `index.html` dashboards continue to be generated by the build; the KG
  Explorer is an additional, not a replacement, view.

## Two separate workflows

The dashboard now controls **two distinct workflows** that share components but are
never conflated:

### A. Research Agentic Audit (`Research Audit` section)

Drives the original `vckg run` pipeline (config 45/46 style): dataset → CodeKG →
agentic LLM loop (KG query planning, retrieval, verification, adjudication) →
audit verdict. Pages:

- **Run Audit** (`/research`): pick a config (defaults to config 46), preview its
  model/backend/KG metadata (API keys never shown), pick candidate functions from
  the validated pair cache, choose reuse/force-rebuild KG and dry-run, then start.
- **Audit Runs** (`/research/runs`): browse `outputs/runs` + dashboard-job runs and
  their per-sample verdicts.
- **Agent Trace** (`/research/trace/:run/:sample`): full per-stage prompt/response
  text (copy buttons, tokens), final verdict + reasoning.
- **KG Query Flow** (`/research/kg/:run/:sample`): q1/q2/q3 query list **and the
  original CodeKG static dashboard embedded in an iframe** (the reference KG
  visualization with search/highlight/path tooling).

**Selection is real**, not faked: the research job writes a job-scoped
`effective_config.yaml` (base config + `dataset.only_sample_ids` /
`only_function_names` / `project_include` / `sample_limit` + job `output_root`) and
runs `vckg run --config <effective>`. The new `dataset.only_sample_ids` /
`only_function_names` fields are applied in `select_samples`, and `vckg run` also
accepts `--sample-ids` / `--function-names` / `--selection-file` directly.

The LLM/model section is left untouched, so the run uses the exact model, backend,
base URL, and API key from your config/environment.

### B. Student Challenge (`Student Challenge` section)

Unchanged: build / serve / validate / evaluate / package, public/private split,
leakage check, admin/student masking. It never invokes the research LLM agent.
